# Developer guide — The Monstrous Sea V2

Start with [docs/README.md](docs/README.md) for documentation authority. Gameplay belongs to [Current game](docs/CURRENT_GAME.md), narrative to [Lore](docs/LORE.md), and unresolved work to [Backlog](docs/BACKLOG.md). This guide owns technical architecture and verification, with no second copy of the gameplay specification.

## Architecture and source navigation

| Location | Responsibility |
| --- | --- |
| `packages/monstrous_core/` | Pure Dart models, content, injected RNG, rules, commands/events, session state and serialized data. Zero Flutter, Flame or `dart:ui` dependencies. |
| `packages/monstrous_sim/` | Headless voyage simulation, bot strategies and generated balance reports. Uses the same core commands/rules. |
| `apps/monstrous_sea/` | Flutter screens and accessibility; Flame battle rendering/effects; the controller and platform storage service. |
| `docs/` | Current reference set, evidence and explicitly separated historical archive. |
| `tools/java_oracle/` | Legacy Java fixtures and parity reference. Its old formulas are not the current game-design authority. |
| `TheMonstrousSea_Original/`, `OriginalProjectIdeas&Planning/` | Read-only legacy source/design references. |

Preserve the [accepted platform boundary](docs/decisions/0001-platform.md): Flutter + Flame presentation, a decoupled pure Dart engine, and Windows desktop as the primary target. Other platform capability is not a claim that every target has been verified.

- `GameSession.dispatch(Command)` mutates core state and returns structured `GameEvent`s. UI/controllers and simulator strategies issue commands rather than duplicating game rules.
- Pass gameplay randomness through `GameRng` / `SeededGameRng`; preserve deterministic replay and isolated sessions. Check existing code rather than guessing APIs from completed task briefs.
- Core models live under `lib/src/model/`; rules under `lib/src/rules/`; narration and player-facing content under `lib/src/lore/` and narration formatters. Historical conceptual `models/ship.dart` paths are not a rename requirement.
- `GameController` bridges session state/events to Flutter notifications, combat logs and storage. Flame renders/plays back events; it must not become a second combat engine.
- Preserve docstrings, rationale and test intent when still applicable. Update stale comments deliberately when related code changes; do not delete compatibility logic merely because its field names describe a retired system.

## Persistence and state lifetimes

[StorageService](apps/monstrous_sea/lib/src/services/storage_service.dart) owns disk I/O. Core [ProfileData](packages/monstrous_core/lib/src/persistence/profile_data.dart) and [VoyageSaveData](packages/monstrous_core/lib/src/persistence/voyage_save_data.dart) own serialization. Windows production saves use `%LOCALAPPDATA%\TheMonstrousSea2\Saves`; other platforms use application support under `TheMonstrousSea2/Saves`. New saves never fall back to temporary storage. See [the save-location and migration policy](docs/CURRENT_GAME.md#persistence-and-presentation) for legacy import and reset behavior.

Storage initialization is shared across concurrent calls. A pending migration journal permits retry before loading a partial save pair; a completion marker prevents stale legacy saves from being resurrected. Existing new-location saves are authoritative. Legacy Documents/temp files remain untouched as backups. `baseDirectory` alone disables migration for isolated tests; pass an explicit `legacyDirectory` to test migration. Do not use production storage in verification. Startup must display a retry state on location/import failure instead of proceeding into a fresh profile.

Keep cross-voyage profile data, current-voyage build/checkpoint data, and combat-only boosts distinct.

Storm-Seer's `stormSeerRedrawRegion` is a voyage checkpoint field keyed to `SeaChart.timesCompleted`, with a missing field defaulting to null. True home departure and succession clear it; merchant/stronghold visits preserve it. `RedrawStormSeerCourses` shares its gate with the UI, changes only offered courses and the usage marker, and preserves any existing Nemesis option. The app ignores stale redraw callbacks during departure or after use. `captainWeaponAccuracyModifier` supplies Overzealous Gunner's additive penalty to both core shot rolls and the UI preview.

`GameSession` synchronizes active captain IDs into derived `ShipState` fields when the ship or traits change. Those fields are not independent save data. Quartermaster applies a reversible slot delta; checkpoint restoration marks the saved slot's provenance before synchronization so it cannot stack. `ShipState.heal(num)` and its preview/inverse helpers apply multiplicative captain modifiers once, round once and cap last; callers pass raw percentage amounts. Paid repairs use a per-visit `PaidRepairWork` ledger, latched only by the first successful purchase; cumulative work/healing/cost rounding prevents split-purchase gains. `ShoreServiceTuning` owns provisional allowances. Whole-battle shore drilling is separate from runic guidance. Carried/pending kit commands preserve exact item ownership and normal continuation. Hull refits now add equal fixed maximum/current HP directly, preserving missing HP independently of healing modifiers and consuming no repair work; see the [fixed-capacity rule](docs/design/voyage-economy.md#hull-refit-hp-growth-and-repair-capacity). Exacting's fractional attack reduction is combat-only state, applied after armor/bracing and before barriers and reset at combat boundaries.

Ram captures `launchRange` for damage/accuracy before closing to Short; its range event precedes the attack attempt and impact. This preserves the launch-dependent charge bonus while presenting the actual impact distance. Harpoon keeps attack-then-pull ordering.

Skirmisher queues `IssueHelmOrder` until `_finishPlayerAction`, after the main action's intrinsic range effects and before the monster response. `previewResponseRange` shares the predictable movement ordering; hit-dependent Pin/interruption is not presumed. Impatient opts into `ExecuteShipSpecialAction(borrowNextAction: true)`, then requires a weapon action; its pending/recovery flags are combat-only. Recovery blocks hardpoints, while helm/belt/Wait & Reload remain legal. The emergency/recovery pass retains the internal `BraceForImpact` command name but grants no evasion; Skirmisher alone does not expose it in the UI. Both used hardpoints retain cooldowns; new encounters and terminal outcomes reset stages. These rules do not add intermediate save phases. Simulator strategies use `captainTraitAction` for legal stage/forced-course decisions.

The checkpoint's `shrineOmenSeed` and `hasClaimedSmugglerGift` preserve voyage/encounter state with safe older-save defaults. Shrine manifestations and taboo selection use a separate deterministic region/leg RNG, so re-entering from the same helm cannot reroll them by consuming unrelated gameplay randomness. Existing Shrine/battle save restrictions remain. Heir offer shuffles use injected RNG; deterministic name collision repair adds no extra draws. The legacy `saltAddict` ID resolves to Exacting Shipwright, while historical captain ledger records are untouched.

`MonsterSpecies.isRegionTitan` is the Nemesis exclusion boundary. `ProfileData` filters unsupported Titan records at construction/assignment; their standalone serialized IDs remain readable for compatibility. Checkpoint restoration repairs only pending Blood Oath offers lacking an eligible target, using stable catalog order without RNG draws. `SeaChart` discards saved offer sets containing a Titan Nemesis, preserving valid offered courses and traveled history. Restoring a helm regenerates missing offers after all profile/voyage context is restored, so the repair cannot leave an empty course-selection screen. Do not reroll already selected captains or rewrite historical death records as part of this repair.

`LineageStore` prepares the root through `StorageService.initializeDirectory`, then owns the validated `lineages.json` catalog and independent `lineages/<slot-id>/` pairs. Existing Documents saves migrate once as Original Lineage with byte-preserved source backups and a pending-import marker. Automatic discovery never scans system temp: an old test profile there was re-importing an unpaid Ironclad grant. Explicitly supplied legacy directories remain opt-in restoration sources. Slot storage uses strict reads. Normal startup uses `LineageMenuScreen`; injected `MonstrousSeaApp.controller` fixtures retain their direct orchestrator entry. A nested navigator keeps slot routes beneath the debug host, preserving F10. Slot controllers enable `retainPreparationCheckpoints` for home/death heir offers. Menu return is limited to fully supported save phases, finishes queued writes with gameplay input disabled and unmounts the route before disposing its controller. Do not broaden that phase set without serializing complete state and testing reward/replay safety. Catalog publication is serialized within one store instance; simultaneous app processes and atomic profile/checkpoint pairs are not provided.

`PauseMenuHost` owns Esc, the modal input/focus boundary and save/return/exit handling. Slot routes supply their lineage label and a post-save navigation callback; direct/debug orchestrators use the same host without a title destination. `canSaveAndLeave` is the shared supported-stop/playback gate. The host fully removes its dialog before popping the slot route, so dialog listeners do not outlive the controller. Nested dialogs consume Esc first; queued writes disable dismissal and controls, and failures remain retryable. Battle marks `isPlayingEvents` before combat dispatch and clears it only after event playback/end delays finish. The orchestrator retains the battle while that flag is set, even if the core already reports loot/death, so parent/menu/settings rebuilds cannot cut its playback short. Pause lets this existing playback continue and blocks new input rather than freezing/replaying the event queue.

The app controller resolves the core's compatibility Rest checkpoint with `TakeHelm` after loot decisions and on old-checkpoint restore, before notifying screens; that command owns stronghold/final routing. Emergency triage remains an engine rule available at the helm. Loot and wreck checkpoints retain pending supplies; wreck snapshots also retain the spent salvage action, name and receipt. Outgoing screens ignore input during AnimatedSwitcher transitions, and the Helm screen freezes its rendered departure view.

`SessionPhase.port` is ancestral home; `SessionPhase.stronghold` is a mid-voyage berth. Stronghold merchants persist their return phase. Legacy regional `port` saves restore as strongholds. Controller persistence snapshots profile/voyage data before awaiting I/O and queues writes, preserving stronghold checkpoints while preventing stale writes after death. Verify completed-Titan saves and legacy migration when changing this lifecycle. Both Havens and strongholds use `VoyageShipwrightView` and the same core costs/caps; permanent progression commands are home-only.

Test fixtures that do not test persistence must set `autoSave: false`; persistence fixtures must inject disposable directories. The app's root `flutter_test_config.dart` also installs a per-suite disposable default via `StorageService.testDefaultDirectory` for the suite's actual `setUpAll`/`tearDownAll` lifetime. Test runner zones do not retain a `main()`-only zone override. `StorageService.withIsolatedStorage` scopes nested asynchronous work; explicit constructor directories take priority. Injected default roots disable legacy import. Never run an unguarded UI fixture against production saves: an audit found older art/UI tests doing exactly that (PT2-27).

A save reset is a separate user action. Documentation/verification tooling must not modify a real player's profile. Use injected storage and isolated game state in tests.

The controller clears the live Chronicle after successful succession/fresh home departure, before appending those events; normal encounters and stronghold departures preserve it. `CombatLogView` owns scrolling, including initial/live-end layout settlement and manual-history pause/resume. `BattleScreen` retains a transient `CombatLogScrollState` across modal reopenings; a new battle starts following latest. `showBattleChronicle` uses a root dialog route, listens for live log appends and restores surviving focus after route removal. Escape dismisses nested inspection/Chronicle dialogs before Pause. Playback continues behind the modal; new gameplay input is blocked. The mutable log list requires a stored prior count to detect appends across widget rebuilds; logs are not checkpoint data.

`showBattleChronicle` owns its scroll controller until the route has completed removal and exposes it through `PrimaryScrollController` above the dialog's focus/close controls. `CombatLogView` accepts that controller, removes its listener on disposal and disposes only controllers it created itself. Latest Messages occupies a separate footer while browsing history. `showVoyagePanel` marks its single reading scroll as primary, including for vessel inspection, so keyboard paging works on desktop. The [logbook audit](docs/archive/README.md#logbook-layout-audit-2026-11-09) verifies wheel/scrollbar/touch/key input, long accounts, fixed close controls, resize, live updates and reopening without changing history ownership or gameplay.

Caldera choice/outcome checkpoints are exceptions to ordinary terminal-checkpoint deletion. `VoyageSaveData` retains `calderaOutcome`, its acknowledgement flag and the exact offered heirs; the controller also checkpoints `expeditionVictory` before choice. `ResolveCalderaClimax` applies the existing consequences once and reads prose from `EldritchLore`; `AcknowledgeCalderaOutcome` changes only the read flag. Keep core `death`/`ended` phases for headless consumers. The app renders the unread outcome before routing to succession or the completed-hunt screen. Claim's outcome clears on succession; slot controllers retain the new heir's home preparation while direct adapters retain their deletion policy. Shatter remains complete across restart. Historical ascension records can render using the current neutral heading without rewriting saved records.

`CalderaSnapshot` is an app-side envelope containing a deep-copied pre-choice profile and voyage, validated as unresolved expedition victory. `StorageService` publishes `pre_caldera_choice.json` with a flushed temporary-file rename. The controller captures it at the choice checkpoint and before resolving a loaded choice, queues it before outcome writes, and retries failed snapshot publication before saving resolved state. `LineageStore.exploreOtherFate` requires a completed original lineage, publishes one independent alternate with a stable hashed ID and `alternateOf` catalog relationship, and resumes an existing branch rather than replacing it. Missing/corrupt legacy snapshots disable branching without hiding the ending. Branch relationships are validated; branches cannot branch again. Existing separate profile/checkpoint crash-atomicity limitations still apply.

`SeaChart` stages private regional groups and conditional cove/consumed-Nemesis alternatives once, with explicit `CourseDestination` identity. Only current offers reach presentation. A selected offer commits encounter difficulty independently of retained grid helpers. Redraw replaces current ordinary entries only; original planned groups retain shrine-floor accounting. Chart JSON owns those groups/alternatives, current destination/difficulty and history; voyage data additionally retains island name/spent duty and specialist merchant return-to-helm. The user chose to reset their old playtest saves themselves; add no parallel legacy-region migration engine. Never delete their saves through implementation tooling.

## Presentation and art

Player-facing terminology is **Ship Fittings** and Standard's **Gun-Deck Bracing**. Keep `HardpointType`, `utility_drill`, `gunneryDrill` and existing serialized fields stable. `HardpointSlot.displayName` resolves the current Standard utility label by its stable ID, while `name` and JSON round-trips preserve older stored names. Battle, inspection and blueprint UI should use `displayName` for fitting labels. The separate island gunnery-training action and Drillmaster trait keep their names and rules.

Use the approved ink-and-parchment palette, fonts and transparent curated nautical PNGs selected through `PilotArt` / `SvgAssetView`. Preserve actual alpha, approved ship/monster silhouettes, sparse contours and asset orientation (ships/weapons right, monsters left). Only approved app art belongs in the Flutter bundle; neither archive belongs there.

Retain the [asset manifest](docs/art/sea_map_art_manifest.json), [revision records](docs/art/sea_map_revisions_v5.json), and [chart-marker provenance](docs/art/chart_icon_prompts.json). These preserve details such as the approved Freighter, Ironclad, Squid and Kraken revisions; generic future styling instructions must not overwrite those choices.

SVG and `CustomPainter` remain appropriate for structural cartouches, compass roses, animated waves, borders and gauges. New entity/item art uses the user's established curated workflow when that work is explicitly scheduled. Do not generate art during a documentation or mapping audit. Missing/misassigned images are tracked in the backlog's deferred-art section.

Battle scenes load/decode illustration bytes before caching successful images; Flame 1.38.2's failed image futures can emit unhandled errors even when awaited in a catch. Failures must leave the scene/event queue usable with a labeled placeholder and retry, while approved art remains unchanged. Retry only failed assets and handle scene removal before asynchronous completion. Do not rebuild the shared Windows output while a player's game is running; widget/engine checks and font-loaded widget captures can verify recovery without replacing that executable/bundle.

`ParchmentHeaderScope` composes host controls across nested navigators; each `ParchmentScaffold` places those headers, its body and its footer inside a single page frame. Hosts must not add external control rows around framed pages. Page fixtures should use the same scaffold to exercise this contract; battle retains its intentional frameless arena.

`ParchmentScaffold` supplies a small pause control when hosted. Screens with an existing settings/control location use `PauseMenuButton` there and disable the scaffold copy with `showPauseButton: false`; standalone screen fixtures retain Settings as a fallback. Keep the battle Chronicle beside the pause control and keep lineage/save details inside the menu.

Preserve readable controls and labels at 115% default text and the larger supported scales. A passing overflow check does not establish that intent, logs or damage effects are readable; review realistic desktop and compact layouts when UI changes.

`BattleScreen` composes a responsive helm/actions dock with two equal-height weapon buttons, separate blessing attachments and a utility row, preserving readiness, belt and trait gates. The bottom footer holds belt/Pause/Chronicle independently of command scrolling; a short/narrow viewport uses a controlled horizontal belt scroll. Explicit footer focus order accounts for the belt's deferred LayoutBuilder, preserving forward/reverse traversal. `BattleLookout` consumes detached displayed monster state; it separates brief intent essentials from a scrollable parchment Inspect dialog. Its optional action notes come from current ship/trait context; damage/sweep caveats are conditional. A side lookout reserves a right scene inset; compact layouts place it above independently scrolling commands. Measured HUD/dock insets bound the art/feedback arena. `MonsterIntent.evaluatePreview(helmAlreadyApplied: true)` accepts an action's response range while retaining the committed helm's collision identity; it must not apply the movement twice. The lookout remains conditional when a fitting can change range; fitting tooltips state their own movement without repeating an action-specific response forecast. These layouts do not change the resolver or event cadence.

Battle playback owns a detached `BattlePresentation`, shared by the Flutter HUD and Flame. `CombatantPresentation` captures immutable effects at their actual mutation boundaries; `CombatEffectsChanged` must not advance HP, carapace or tentacles from those snapshots. Dedicated outcome events carry exact endpoints and explicit combatant sides. `CombatRangeChanged.mover` identifies who actually moved; `instigator` identifies the cause of a pull/push. Range cues anchor to the mover and never infer actors from relative distance or narration. Healing/extra damage and named blessing riders have structured source facts; barrier absorption is distinct from aggregate non-barrier mitigation. Snapshotting only after a nested rule helper returns loses intermediate effects. Ghostwake masks its temporary accuracy-only obscurity bypass in captured frames. Decision controls synchronize after playback, while health/defense/effect consequences arrive through events; action-dependent forecasts are suppressed while locked. Preserve final impacts before terminal combat resets and keep the existing playback/input/save gate. These projections are transient and do not change checkpoint serialization. Feedback lifetime is independent of the event queue: ordinary outcome waits are 400–500 ms; attack-name lead is 100 ms. Per-side stacks retain at most three measured cartouches, newest nearest the actor, across commands until expiry or capacity eviction. Compact arenas may evict earlier to fit. Cached text layout reflows on resize/insets/font/text-scale changes; synchronous idempotent dismissal releases painters even for labels evicted before Flame mounts them. Reserve feedback space only from arena height beyond the art allowance, so compact art does not collapse. Do not wait for decorative expiry before unlocking input. Barrage pacing is strike-based: only the opener honors reading holds; every wait from strike two uses half its base duration, capped at 200 ms, so a newly encountered outcome cannot restart the slow introduction.

`ShipState.effectiveEvasion` is the shared ship dodge threshold for combat, HUD and effect readouts; it combines current evasion, captain bonus and live Basalt effects with the existing 0–95 cap. `MonsterState.effectiveEvasion` shares Pin/Flare handling and the actual 0–100 d100 bounds. Do not duplicate these formulas in Flutter. The removed global range modifier stays removed. `CombatantPresentation` freezes captain Boon/Quirk IDs alongside current effects; apply that context to detached actors during initial/idle synchronization and playback. Read HUD percentages from those displayed actors so later source mutations cannot leak ahead of causal events.

Pass the actor's `isGrappled` into `isWeaponTypeUsableAtRange` for active combat decisions. The session, direct volley rule, Impatient eligibility, battle buttons/emergency reload and simulator bots share this helper. Flutter supplies the displayed ship state. Static equipment range tables may omit the actor flag. The Ram movement/preview guard remains separate from attack availability, so a Grappled ship can strike at Short but cannot initiate a Medium charge.

`BattleScreen` measures the scaffold body's constraints after host headers, rather than budgeting against the whole MediaQuery window. Its bounded HUD scroll viewport owns `_statusKey`, so arena insets measure visible status height rather than the full offscreen effect row. Integrity precedes stats/effects. Dedicated status, lookout, command and belt controllers keep their scroll positions independent. Desktop arena room also reserves the brief lookout forecast; longer reports retain a visible scroll indicator. `combat_layout_matrix_test.dart` checks all hull/trait pairs, readiness/recovery stages, full belts and multiple effects with real game fonts and the normal debug/pause hosts. Its paused Flame fixture awaits component lifecycle readiness and verifies two mounted combatants before inspecting their bounds or capturing proof.

When the compact command budget falls below 200 logical pixels, the lookout joins the command scroll above the helm/fittings instead of exhausting the fixed column's height. The belt/Pause/Chronicle footer remains fixed. `HullGauge` wraps its label; fitting buttons opt into unlimited `InkButton.labelMaxLines` and subtitle lines while preserving the equal-height weapon row. Other buttons retain their existing two-line label default. Compact monster-name ellipsis has a full-name tooltip. The retained rest screen stacks vessel details below its art and wraps stats/workbench headings; debug numeric-field errors allow three lines. `final_layout_sweep_test.dart` uses memory-only/pending storage substitutes, cancelled native exits and injected artwork failures, freezing only loading tickers for stable captures. Its [inventory](docs/archive/README.md#final-layout-sweep-2026-11-09) ties the remaining branches to the earlier screen/dialog audits.

`LootSuppliesView` shares its responsive row/column layout with the footer actions: below 500 logical pixels, unwrap Expanded children into a full-width column and retain gaps. Compact item actions have an 8-pixel lead-in so patch/jettison controls do not share a border. Keep command callbacks and pending/carried ownership intact. `encounter_layout_matrix_test.dart` uses normal debug/pause chrome, verifies scroll reachability and complete action bounds, and checks action-label ellipsis with real game fonts. It covers service/trait availability, full belts, five blueprints, all shrine powers and supported regional shores. Rendering/tab/inspection review must not change ship/profile/chart, stock, pending items or repair work.

`PortScreen._responsiveRow` retains horizontal Expanded children on wide layouts and unwraps them into a column on compact layouts, converting horizontal gaps into vertical gaps. It serves home summaries and Covenant tabs/actions; title/status pairs wrap independently. Keep upgrade/commission/pact callbacks intact. `InkButton.subtitleMaxLines` defaults to two; only the selected user-entered lineage label opts into unrestricted wrapping. `home_layout_matrix_test.dart` reviews existing screens through normal debug/pause chrome with autosave-disabled controllers and memory-only lineage storage, preserving profile/ship/chart and save snapshots during browsing.

`DeathScreen` separates heir heading and trait presentation into responsive helpers, using full-width names/descriptions on compact cards while retaining the original wide rows and text styles. Selection and name controllers remain in the parent state. `lifecycle_layout_matrix_test.dart` uses isolated sessions and snapshots profile/ship/chart/offers/ending state during reading, selection and local input edits. Its test binding cancels native exits. Allow Material validation animations to advance before capture; freeze only the intro's repeating ticker after full reveal (or at the intentionally partial opening), leaving production animation/timing unchanged.

## Linked mechanic help

`MechanicScope` passes the displayed ship/monster and current region into `MechanicText` and `MechanicTooltip`. Battle scopes use detached presentation actors, never the already-resolved live encounter. Shrine descriptions supply the prospective blessing; shared `magmaBurnDamage`/`arcDischargeDamage` helpers keep base numbers aligned with core. Magma/Tempest/Corroded use their existing highest-tier rules; Shaken uses its Broadside tier or captured active penalty. Home Flare details retain base stats, and active/inspection Illuminated help uses captured bonuses or the existing utility multiplier. `currentItemDescription` presents approved Hull Patch Kit/Chain-Shot copy for stored items without rewriting saves.

Keyword anchors use overlay portals, semantic activation, hover, keyboard and long press. F1 opens action help without dispatching the action; keyword activation opens its explanation. Parent ownership keeps linked cards open, suppresses cyclic ancestor links and cancels close timers on disposal. Cards prefer space beside the parent, clamp to the viewport and scroll if needed. They have no visible close icon: Escape, outside interaction and the semantic Dismiss action provide dismissal. Keywords use medium-bold accuracy-gold text without an underline and a help cursor. The inner keyword Text disables its own text scaling because WidgetSpan already scales it with the surrounding paragraph. Fitting help states its own effects and computed weapon opening accuracy. Target dodge belongs to the monster HUD; fitting tooltips omit the secondary “After action” prediction. The [typography follow-up](docs/archive/README.md#tooltip-typography-follow-up-2026-11-10) covers rendered scaling and real fitting messages. Definitions belong in contextual help rather than repeating interaction manuals in every action description.

`MechanicTooltip.hoverInset` defaults to zero. Battle weapon/utility fittings opt into a 12 logical-pixel inset for starting mouse help, capped at a quarter of each target dimension. Moving into the interior opens help; its full anchor retains existing open help. This prevents exposed neighboring button edges from replacing a card during pointer travel. Clicks, F1, long press, keyword targets and ordinary stat help retain their full areas. The [handoff follow-up](docs/archive/README.md#tooltip-handoff-follow-up-2026-11-10) reproduces the direct Signature-to-Carapace path at 115–130% text.

The [tooltip sweep](docs/archive/README.md#tooltip-sweep-2026-11-10) uses `OverlayPortal.overlayChildLayoutBuilder` and transformed bounds so help follows scaled/scrolling sources. A source outside an ancestor viewport dismisses its branch after layout. `_HelpPosition` lays out both the card and a small translucent hover region in the gap: other mechanic anchors on the same route consult that region before opening, while pointer clicks still reach underlying controls. Keep its protection limited to short gaps. Nested cards choose free rectangles outside all ancestor cards, adapting width/scroll height without changing text size; normal horizontal and vertical placements remain available. Source inventory and real screen walks complement the retained keyword/input matrix. Read-only test fixtures must not initialize player storage or dispatch action/purchase commands while browsing help.

Open help anchors share one early key handler so hover-opened explanations consume Escape before gameplay shortcuts without stealing focus. It closes the most recently opened help on the current modal route, including key repeats; newer dialogs retain priority. Closing/disposal unregisters anchors and removes the handler when none remain. Placement checks all ancestor card rectangles before choosing available side space, then uses the bounded compact fallback. The [overlay audit](docs/archive/README.md#overlay-layout-audit-2026-11-09) covers this lifecycle together with Pause save gates, wrapping Settings headings, live font changes and all hull inspections at larger text sizes.

Mouse-opened help is transient even if focus remains in a card. Keyboard/semantic/touch openings focus the reading scope; F1 can take over existing hover help. Pointer kind distinguishes a mouse click/long press from keyboard/touch activation, so mouse clicks do not latch or unexpectedly toggle a hovered keyword. The visible-help registry also defines one branch per parent/route. Sibling opening closes the old branch; descendants share the root's TapRegion group, and outside taps close that family. Branch activity includes hovered descendants; exits schedule ancestor checks without restarting an already pending timer during child teardown. Close/dispose removes registrations and restores surviving focus for explicit dismissal. Keep [the player follow-up regressions](docs/archive/README.md#tooltip-hover-follow-up-2026-11-10), including rapid switching, mouse focus retention, hover gaps, long press, semantic Dismiss and nested keyboard restoration, when changing this lifecycle.

## Tooling on Windows

Dart/Flutter analysis and test workers can stall in restricted Windows sandboxes because they use child processes and local IPC/loopback. Use the execution tool's supported permission override when needed; the available API here is `sandbox_permissions: "require_escalated"`, not the historical `BypassSandbox` / `manage_task` arguments.

Run commands from the relevant package directory, and never analyze the monorepo root indiscriminately. Use the tools actually available in the current session; a historical Flutter-driver or MCP capability description does not establish present access. Poll a running process through its returned session identifier at reasonable intervals and report material progress.

## Development playtesting

The root README owns [playtest menu access and launch instructions](README.md#playtest-menu-debug-builds). `MonstrousSeaApp` wraps the normal orchestrator in `PlaytestHost` only under `kDebugMode`. F10/the debug toolbar opens a separate route; `PLAYTEST=true` opens it directly and defers mounting the normal game until the route closes. Release/profile builds have no entry point, and scenario creation itself rejects non-debug builds.

[PlaytestConfig](apps/monstrous_sea/lib/src/playtest/playtest_config.dart) is an app-side debug adapter, not a new core gameplay command or progression entitlement. It creates a fresh profile/session with an explicit seed, the selected blueprint/ancestral tier, a factory-built hull, real `temperShipHardpoint` upgrades, and canonical `HardpointBlessing`s. Region advancement uses the chart's normal generation. A synthetic rest checkpoint approaches the helm without triggering home's intentional new-voyage reset; Titan launches use the real convergent heading and encounter startup, including regional hazards/intents. Caldera launches provide a test Core and the actual ending decision. Subsequent rewards, strongholds and endings use normal commands.

Each scenario controller explicitly disables autosave and injects a separate temporary storage path, with implicit legacy migration disabled. No test folder is created during normal scenario use. Never reuse the live controller/profile/storage for a test build. Menu edits remain available across relaunch, but every launch creates a fresh independent controller; outgoing widgets unmount before their controller is disposed. Test sessions are disposable and do not survive application restart.

Run checks appropriate to the change and inspect the actual diff. The commands below are the package-level baseline; fixed counts in archived receipts are historical, not current pass criteria.
